    UI composer

    A background pass that decides what the investigation screen shows while an investigation runs: evidence cards as data is collected, and a service graph that grows with the investigation.

    Nothing about a card's type, its visual or the services it belongs to is decided in code. A cheap model decides, from instructions in the content catalog (agents/ui-composer/AGENT.md). Falcon batches, bounds, validates and emits.

    Turning it on
    FALCON_UI_COMPOSER=true Off unless set.
    Catalog agent ui-composer Its instructions are the pass's prompt. The file is neubird-content/agents/ui-composer/AGENT.md and must be in the catalog the deployment (or the desktop's rsync mirror) mounts. With no such agent, or no instructions, the pass stays off and the run is unchanged, with nothing in the log to say so.
    Session type Incident and alert investigations only. A chat, a Home ask or a sweep inside another run never gets one.

    The model is falcon's digest model (DIGEST_MODEL_OVERRIDE, else the tier's digest model, Haiku by default), the one the interim summary uses. INFERENCE_MODEL_OVERRIDE does not move it. The agent's metadata.model is required by the catalog loader and is informational here.

    How it runs

    finishToolCall hands each finished call to the composer and returns at once. Calls that finish within 1.5 s of each other share one request, at most 8 to a request, at most 40 requests per investigation. One request is in flight at a time. The model is shown a sample of each result (1,500 chars at a record boundary), the call's reason, source and input, the question, and the graph drawn so far. The instructions and the question are a prompt-cache breakpoint.

    The reply is a JSON object of up to 2,048 tokens: the request asks the digest call for that, because the digest default is 1,024 and a batch of cards, chart specs and edges can pass it. A reply cut off at the cap is unreadable and the batch is dropped whole, with a warning in the log (ui composer: reply cut off at the output cap).

    It never fails an investigation: a request that errors, panics or returns something unreadable draws nothing, and Execute stops the pass when the run ends: a call that finishes in the last 1.5 seconds, before its batch has been sent, gets no card. An investigation spends longer than that writing its answer, so in practice only the last call of a run that ends at once is lost. Bookkeeping and presentation tools (write_todos, show_*, emit_*, report_findings, citations, workers) and failed calls are never composed. A list of signals (browse_incidents, list_incidents, list_incident_alerts) gets a card but no chart or table: signals are drawn by the signals list control and nothing else, the same rule as Home. The request's cost counts toward the run's like any digest call.

    Frames

    Both are tool_data frames, like show_chart, and pass raven's relay verbatim.

    show_evidence — one card. tool_use_id on the frame is the investigator's call it is about. input_json:

    {
  "id": "ev-toolu_01…",
  "tool_use_id": "toolu_01…",
  "tool": "loki__query_logs",
  "type": "Application logs",
  "title": "Checkout errors are climbing",
  "source": "Loki",
  "reason": "see whether checkout is erroring",
  "insight": "Errors rose from 4 to 31 in twenty minutes.",
  "services": ["checkout-api"],
  "records": 3,
  "visual": { "kind": "chart", "spec": { "title": "…", "mark": "bar", "x": {…}, "y": […] } }
}

    id is ev- plus the call's own id (a second card for the same call gets -2), so ids stay unique across a session's runs. type is free text the model chose. source, reason and records come from the call, not the model. visual is {kind: "chart" | "table", spec} or null; the spec is a show_chart or show_table spec, checked by the same code (checkChart, checkTable), and raw_output is {columns, rows}, read from the call's own full result. A visual that cannot be drawn is dropped and the card kept. A card whose tool_use_id is not a call the model was shown is dropped; a batch of one call needs no id.

    show_graph — what changed in the graph, never the whole graph. input_json:

    {
  "anchor": "checkout-api",
  "nodes": [{ "id": "checkout-api", "label": "checkout-api", "kind": "service", "status": "failing", "ref": "service:checkout-api" }],
  "edges": [{ "from": "checkout-api", "to": "orders-db", "kind": "calls", "why": "checkout queries orders-db on every request" }]
}

    A client merges nodes by id and edges by (from, to, kind). An edge is only sent when both of its ends are in the graph; a service a card names that the graph lacks is added to it. anchor is sent once, when it is first set.

    Not covered

    The pass runs only for a run that persists: a SuppressPersist run (a sweep inside another run) is ephemeral and gets no composer. ui_composer_run_test.go drives a real Execute against a mock model and proves the cards and graph reach the run's tool_data lane, and that a chat, an unset flag and a missing catalog agent each compose nothing.

    The frames are not persisted: a reload during a run replays them from the Redis stream (about 30 minutes); after that they are gone. Persisting them for a finished investigation is separate work.

    Relation to Home's generative pipeline

    Home's pipeline (docs/api/infer-endpoint.md, neubird-ui-core/apps/desktop-new/docs/genui.md) is a different thing with its own agents: home-router, the executors, home-composer. This pass is ui-composer, a background pass inside an investigation, and the two names are not shared.

    • Frames. Home's route, findings, ui and ui_done are top-level frame types. Raven's relay forwards tool_data and structured_output verbatim and silently drops any other type, so those four reach only a client talking to a local sidecar. This pass's frames are tool_data, so they reach a browser through raven. The same holds for findings: report_findings reaches a browser as tool_data with tool: "report_findings", not as a findings frame, and raw_ref rows do not travel, so a dataset must carry its rows inline.
    • Vocabulary. A node is an entity (id, kind, label; status and ref in attributes), an edge is a relation (from, to, kind; the why in attributes), a card's insight is a statement about the services it names. The findings contract has no slot for a card's type label, title or integration name, and deliberately no presentation (the chart spec). That is why this pass keeps its own two frames today. Moving to findings, so that one contract serves Home and the investigation, is the planned step; it adds those few optional fields and an adapter on the client.

    The desktop app no longer uses this pass (2026-10-15). There an investigation runs on the local sidecar through Home's pipeline with surface: "investigation": the router is skipped, the investigation intent runs investigation-executor, which calls topology_lookup and topology_explore and reports entities, relations, claims and evidence through report_findings as it goes, and home-composer writes the narration (internal/server/home_pipeline.go; the contract is genui.md, "The investigation screen"). The client draws the graph from those findings, so the gap described above (no slot for a card's type, title or integration) is a gap in the findings and shows as an unlabelled card there. This pass remains for an investigation that runs on a deployed falcon behind raven.
