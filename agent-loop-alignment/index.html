    Agent loop alignment: state substrate under the verified pipeline

    Diagnosis

    A prompt-mirror run (trace a2c0aa2e, claude-code CLI, opus-5, our MCP tools, our prompt verbatim) found the adjudicated source-level mechanism on api_500_sg1 in a single 14.7-minute pass. Its system prompt contains no investigation methodology — no trigger families, no lifecycle, no verification doctrine. The behavioral difference is not prompt content; it is that claude-code is the harness this model was RL-trained in, and falcon's pipeline replaced or disabled the native affordances:

    Working state claude-code falcon pipeline (before this change)
    Private reasoning adaptive thinking, interleaved between tool calls, ON by default (MAX_THINKING_TOKENS default ~32k; only 0 disables) {type: "disabled"} sent explicitly when no effort configured (client.go thinkingParam)
    Plan TodoWrite list — persistent artifact, staleness-nudged, survives context churn !write_todos (banned as "planning theater"); plan lives only in ephemeral prose
    Evidence full tool results kept; one structured compaction near the window limit continuous tier-1 compression of oldest results + tier-2 drops (trimMessages)
    Loop guidance trained phrasings in the system prompt (parallel tool calls, act-when-ready) absent from the harness layer; ad-hoc lines in the SOUL

    Falcon compensates with instructions (SOUL standards) and terminal gates (emit validation, ledger, referee). Those are the pipeline's differentiator — the referee has caught onset fabrication and rule-widening the mirror missed — but they audit the output; nothing maintains working state across a 50-turn run. The recurring failure shape follows: late-run wrap-up bias, plans that evaporate (run 3 never returned to check its mechanism's predicted log signature), unknowns declared at whatever instrument the run was fluent in that day.

    Architecture: match the SDK's own preset+append split. The harness carries the loop layer (what the claude_code preset provides and the model expects); the SOUL carries the domain layer (families, lifecycle, signatures, instruments); the gates and referee stay downstream, unchanged.

    Layers

    Layer 1 — reasoning state (this change)

    thinking_mode: high on RcaInvestigator and RcaReferee. Maps to adaptive thinking (thinking: {type: adaptive} + output_config.effort: high). Structured-output emit turns still force thinking off (API constraint — client.go json_schema note); acceptable: emits are mechanical, the reasoning happened before them.

    Layer 2 — plan state (this change)

    A harness-owned plan tool (internal/ai/plan_tool.go), built the owed_checks way, for both pipeline agents. NOT write_todos: that tool's survival machinery is dead exactly where the pipeline needs it — the staleness and completion nudges are gated off for structured-output runs (pendingTodoStaleNudge: rs.endsWithStructuredOutput), which every pipeline agent is, and the disable_write_todos ConfigCat gate can strip the tool deployment-wide.

    plan reuses the write_todos item vocabulary (statuses, full-replace semantics — the task-list contract the model is trained on) with state on the run and a staleness re-render that stays live for structured-output runs: after 8 client tool calls with no plan update, the open items are re-rendered into the tool-result message (up to 4 times per stage). The re-render is the survival mechanism — the current plan re-enters recent context, where trimming cannot eat it. Pipeline agents (denied elsewhere, same pattern as owed_checks); the referee gets it too (no ledger dependency), and so does the Challenger family (rs.claimsAgent, agents delivering through store_and_verify_claims) — it denies write_todos for the same reasons, so without plan it would have no planning device at all. Division of labor, so the earlier "planning theater" concern stays answered:

    • plan = the plan. Model-owned, free-form, revisable, advisory. Where intentions survive context growth ("verify the signature against the nginx logs" stays open until done).
    • owed_checks = the contract. Harness-enforced debts (seeded checks, named candidates, confessed gaps) that block the claims emit. Unchanged.

    Layer 3 — evidence state (designed here, next change)

    Target: for pipeline stages, replace continuous trimming with keep-until-threshold + one structured compaction turn at ~85% of the context budget. The compaction summary is generated with a fixed schema: established facts (each referenced by catalog idx — the evidence ledger survives outside the context window, which makes falcon's compaction more lossless than claude-code's), the current todo list verbatim, open owed checks, and key raw excerpts. Existing tier-1/tier-2 trimming remains as the emergency backstop only. Not implemented in this change: it touches trimMessages call sites in the core loop and needs its own tests (compaction fires once; catalog refs resolve post-compaction; pinned claims evidence survives verbatim).

    Layer 4 — loop guidance at the harness layer (this change)

    New prompt section prompt-sections/agent-loop.md, injected for pipeline agents (pipelineRCAAgent) and the Challenger family (rs.claimsAgent), carrying the model's trained loop phrasings (parallel tool calls; act when ready). Both qualify on the same ground: their SOULs are epistemics and delivery only, with no loop mechanics of their own. The SOUL's custom batching sentence is removed — superseded by the trained phrasing at the correct layer. Blast radius: those agents only; no other agent's prompt changes.

    Measurement

    One layer-set per run, graded against the two adjudicated keys (eval/probes/keys.md: qos_consumer_de1, api_500_sg1), binary RCA-hit first, then wall-clock and cost. The api_500 probe is the sharpest test: the signature hop (source read → back to telemetry) is exactly the behavior the plan/thinking substrate should produce without further prompt additions.

    Which layers the Challenger family inherits

    Challenger (docs/challenger-agent-design.md) is not a pipeline stage — it has no verify_with, so no driver enters rcapipeline.Run — but it delivers through the same evidence discipline, so the layers were re-gated on rs.claimsAgent rather than copied:

    Layer / mechanism Challenger Why
    Layer 1 — thinking mode inherits its def's thinking_mode Nothing pipeline-specific
    Layer 2 — plan yes Denies write_todos, so this is its only planning device
    owed_checks + seeded debts yes, with a per-run ledger Debts block store_and_verify_claims the way they block the claims emit
    [call_idx N] result stamps yes It references evidence by call_idx too; without stamps it re-lists the catalog per claim
    Layer 4 — agent-loop.md yes Its SOUL carries no loop mechanics either
    Layer 3 — pipelineContextBudgetTokens (140k) no, deliberately The 140k figure is sized against max_tokens: 32000 on a 200k-window model; Challenger runs at 16k and, unlike a pipeline stage, hands its transcript to runSynthesis afterwards. Widening it changes what synthesis pays for. Revisit with measurement, not by analogy
