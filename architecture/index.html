    Falcon Architecture

    A reference for the main entities, data structures, and execution workflows of the falcon agent — one Go binary (neubird) that runs as a terminal TUI, an HTTP sidecar (--server), and a Redis-backed job runner.

    Companion doc: MEMORY_SYSTEM.md covers the durable memory store (ACE) and assimilation pipeline in depth; this doc covers the agent engine, including short-term (in-context) memory management.

    Key facts:

    • All telemetry access is via ACE MCP. There is no direct-Postgres mode and no internal/db package; exec_sql, list_tables, describe_table, etc. are ACE tools. ACE URL derivation: ACE_URL env wins, else TrimSuffix(raven_url, "/api") + "/ace" with the login access token as Bearer; internal deploys fall back to http://ace/private/ace.
    • The desktop launches the sidecar as a child process and authenticates with a per-launch shared secret. The secret and session credentials arrive on stdin at spawn (internal/bootstrap, gated by NEUBIRD_BOOTSTRAP_STDIN=1) — never in the environment, never on disk.
    • authMiddleware enforces X-Desktop-Secret on every route except /health; when no secret is configured (hand-run --server, default :8080) the server is open.

    Agents (sub-agent personas)

    An agent in falcon is an AgentDefinition: a named persona with a model, tool/skill allowlists, context-section opt-ins, and behavioral flags. The engine (internal/ai) is persona-agnostic — everything persona-specific is data.

    • A definition file is YAML-ish frontmatter (--- … ---) parsed by parseAgentFile (internal/agents/agents.go). name and model are required.
    • If a prompt directory agents/<Name>/ exists, agents.LoadPromptFor assembles its fragment files into the complete base prompt and the registry persona is dropped (see executeInternal: runBasePrompt = filePrompt; runPersona = ""). Otherwise the persona string rides on top of the shared Analyst.md investigation base.
    • prompt_dir: points an agent at another agent's directory, so two definitions can share one body of doctrine while differing in model or budget (ChallengerSonnet → agents/Challenger/, L1Laconic → agents/Laconic/). The redirect is resolved from the definition, so only the def-aware loaders (LoadPromptFor, LoadStablePromptFor) honour it — the name-keyed LoadPrompt(name) takes a directory name and cannot see it.
    • BOOTSTRAP.md is included once, then deleted from disk (never served from the embedded FS, which is immutable). LoadStablePrompt skips it for idempotent syncs (merlin SyncToRaven).
    • The registry is guarded by allMu; iterate via agents.Snapshot() and read via agents.Get(name) (heap copy) — never range agents.All directly.

    Roster

    Built-in registry: Responder (Haiku, fast triage, own prompt dir), Analyst (Sonnet, default investigator, Analyst.md), Architect (Opus, persona on the Analyst base).

    Frontmatter personas shipped in agents/ (non-exhaustive; each is definition + optional prompt dir): AssistedAnalyst, QuickAnalyst, SeniorAnalyst, StaffAnalyst, Laconic + L1Laconic, Challenger + ChallengerSonnet, Scout, Ops, Craftsman, Explain, IncidentReporter, IncidentFilterBuilder, OnCallConfigBuilder, ChannelSummary, SlackListener, Sentinel, Watch, Workflow, TaskBuilder, CreateSkill / ValidateSkill / Eval, Synthesis, Scratch, GapMapper (+ its referee GapReferee), PRRiskScorer, and the memory pair ExecLearningsAgent + MemoryAssimilator (see MEMORY_SYSTEM.md).

    Depth tiers (what the UIs actually ask for)

    The UIs do not name agents. neubird-ui's prompt-bar depth picker and falcon-app's composer mode chip both send a tier alias in the request's agent field, and internal/agents/tiers.go decides what it stands for:

    Tier Agent Intent
    Ask QuickAnalyst Answer and hand off, rather than investigate
    Assisted AssistedAnalyst Bounded progress, then hand the next step back to the user
    L1 L1Laconic Bounded investigation, driven to a conclusion — Laconic's doctrine on Opus 5.5 at low thinking effort (the model rejects a thinking disable)
    L2 Laconic The same investigation with extended thinking on (high effort)
    L3 Challenger Self-refuting deep analysis on Opus
    • Owning the table here is the point: retargeting a tier is a falcon change, not a coordinated release of two UIs. Before this, falcon-app's L1 meant Laconic while neubird-ui's meant Analyst.
    • Not every UI offers every tier. Assisted appears in neubird-ui's agent list only, behind the enableAssistedTier ConfigCat flag, and falcon-app never sends it. That is a decision about who is offered a depth, not about which aliases resolve: falcon answers Assisted for anyone who sends it, so the flag cannot desync from a rollout. It sits between Ask and L1 — it investigates, unlike Ask, but stops at six tool rounds with structured follow-ups instead of driving to an answer, which is why it is its own tier rather than a cheaper L1.
    • Aliases are reserved and matched case-insensitively. resolveAgent consults the tier table before the registry, so an agent (or raven row) named L2 is unreachable by name — TestTierTargetsAreShippedAgents fails the build if one appears.
    • Concrete agent names still work on the same field: Sentinel, the builder agents and raven-authored agents are unaffected.
    • The session is stamped with the resolved agent (def.Name), so a run started as L2 is recorded and filterable as Laconic.
    • L1 and L2 are two agents rather than one agent at two thinking settings on purpose. Model and thinking can only be pinned per agent name (AGENT_MODEL_OVERRIDES, the one lever that outranks a deployment-wide ConfigCat InferenceModelOverride — note frontmatter model: is the weakest signal, see InferenceModelLabel), and a distinct name is what makes an L1 run distinguishable from an L2 one in session metadata, agent-name filters and evals. L1Laconic shares Laconic's doctrine via prompt_dir: (one copy of the SOUL), the same arrangement ChallengerSonnet has with Challenger; TestLaconicTiersDifferOnlyByThinking fails the build if the pair drifts apart.
    • FALCON_AGENT_TIERS retargets tiers without a rebuild: l3=DeepAnalyst,l1=Analyst. Unlisted tiers keep their defaults; a malformed or unknown entry is logged and ignored rather than emptying a tier. Per deployment, the same value goes in the agent_tiers key of the llms ConfigCat squad JSON (raven forwards it top-level; FetchLLMEnv maps it to the env var set-if-empty, so a pod-level env var still wins). Like llm_tier, it is read at boot — restart falcon after changing the flag.

    Entry points: agent.Run (fire-and-forget goroutine) → agent.Execute → executeInternal → runLoop. All in internal/ai/agent.go.

    Notes that the diagram compresses:

    • Timeout contract (unchanged, load-bearing): Execute strips the parent deadline via context.WithoutCancel, then applies TIMEOUT_SECONDS env (the squad's investigation_timeout_seconds) → def.Timeout → 10 min. context.AfterFunc still honours explicit cancellation. Never pass a deadline-bearing context — a parent deadline firing first is indistinguishable from a user cancel and misclassifies the run as CANCELLED. Callers set def.Timeout instead.
    • Deadline recovery — a timed-out run never ends as a bare failure. When the deadline fires and a synthesis pass qualifies, synthesis runs on synthesisContext — a fresh budget from context.Background() with its own 3-minute cap (only explicit user cancel propagates in). When no synthesis qualifies, runTimeoutSummary forces a terminal wrap-up on the same fresh-context mechanism: one tools-less call on the run's own model producing a final summary (streamed, appended to history, stored via rs.synthesisText with a time-limit caveat, PROMPT_STATUS_COMPLETED); if that call fails, the floor persists the already-gathered narrative (collectAssistantText) with the caveat. Only when even the floor is empty does the run surface as FAILED with the plain timeout note. Structured-output agents (ends_with_structured_output) skip the prose wrap-up (it would fight their emit flow), as do agents with disable_synthesis set (e.g. Watch, Sentinel) — they rely on terse, machine-parseable output rather than prose, so they keep the plain timeout note instead. Worst-case wall clock is therefore def.Timeout + up to 3 min of wrap-up.
    • Deferred web_search: a tool_use turn can carry an unpaired server_tool_use (Anthropic defers the search so client tools run first). The continuation turn must send back only tool_results with the unpaired block intact, so the quick-finalization transition is skipped/deferred on that turn (resolveDeferredSearch, pendingQuickFinalization).
    • Confidence machinery: a run is scored once, at the end, by runConfidencePass (agent.go): after the report pass writes the report, one more call on the same prefix plus the report asks for a single CONFIDENCE: NN line against a fixed rubric (confidenceRequestText). That score is recorded on the ProgressTracker and is what the PDF, the turn snapshot, raven upload and the Langfuse final_confidence / confidence_source: report_pass metadata carry. There is no model-facing confidence tool and no confidence nudge. The interim summarizer does not set the run's confidence: an earlier design fed its score to the tracker, but it saw only a delta and never the report, and its last guess became the run's permanent confidence. Consequences: the tracker's confidence — and so progress.confidence and interim_summary.confidence — is 0 for the whole run until the report pass scores it; runs that end without a report pass (no sources, disable_synthesis, structured-output agents, health/cost synthesis) fall back to completionConfidenceFloor (75) at SetDone, and the Langfuse final_confidence is then omitted because the floor is not a judgment. One legacy exception: emitServerToolDone records a flat 70 when a server-side web_search returns URLs and nothing has scored yet, so a run that used web search shows 70 mid-run, and keeps it if no report pass follows. Live (provisional) confidence: the summarizer ends each update with a provisional score on the same bands, emitted as interim_summary.provisional_confidence. It is display-only — never recorded on the tracker, never stored, never the final score.
    • Cost cap: checked at the top of each turn from the context's cost accumulator. The turn that crosses the cap completes; the next one doesn't start. costCapExceeded injects a framing note so synthesis explicitly says the investigation is incomplete.
    • Empty-response and stream retries share a bounded budget with backoff and do not consume iterations; the budget deliberately does not reset on thinking-only turns so a persistently silent model can't farm fresh retries out of the no-text nudge cycle.
    • Iteration cap (100 per batch, 200 for pipeline RCA stages, or cfg.MaxIterations): the loop asks for a summary (requestSummary), fires OnContinuePrompt, and blocks until Continue() — server/auto-continue callers keep going, TUI asks the user.
    • After the loop, structured-output agents run their own save/confirmation gates (ensureIncidentFilterSaveConfirmation, QuickAnalyst/AssistedAnalyst handoffs) instead of the generic nudges.

    Execution side (executeTools → executeTool): built-ins dispatch by name in a big switch; anything else routes to its recorded MCP session via mcpSessions[name]. MCP results are text-content joined then JSON-parsed — a tool "error" is (text, isErr=true), not a transport error. SQL errors trigger auto-learning (autoSaveColumnLearning, autoSaveGroupByLearning) and a MANDATORY save_learnings nudge appended to the tool output. Tool outputs are truncated for context (truncateForContext), summarized for the TUI (summarizeToolData), and counted into RecordDataRead only when isDataTool — memory/meta/bookkeeping tools are excluded by name.

    Background tool calls

    A tool call normally blocks its turn. A tool that sets Backgroundable may be started detached: the engine returns a placeholder tool_result immediately, runs the call on the run's context, and delivers the real output as text on a later turn. Delivery is automatic; each call also gets a short handle (bg_N) named in its placeholder and its delivery header (with the call's arguments and, on claims and pipeline runs, its call_idx), so the model can tell calls of one tool apart and aim wait_for_workers or cancel_workers at a single call. Two routes reach the detached path, and Backgroundable gates both: the model asks, by setting a background boolean the tool declares on its own schema; or the tool's own BackgroundDefault reads the call's arguments and says this shape always detaches. The second exists because a prompt is a suggestion — a tool whose contract already pins how a call runs should not depend on the model remembering a flag — and it keeps per-tool policy in the tool rather than the engine.

    A third route is the deployment switch (FALCON_TOOL_BACKGROUNDING_ENABLED), which also promotes a call that simply outlives FALCON_TOOL_BACKGROUND_AFTER_MS — adopting the in-flight call where it is rather than killing and retrying it. That route is an allowlist: only calls that leave falcon for a customer system (toolHitsCustomerSystem, the same rule classifyTool uses to label a call with the service it queried), minus schema probing (backgroundSchemaLookup). Bare ACE names — memory, inventory, skills, incident and alert writes — are orchestration the next turn is built from, and a detached write can be cancelled mid-flight and then reported as having produced nothing; neither belongs off the turn. backgroundExcluded names the handful that must finish regardless of how they are declared. The promotion placeholder says how long the call had already run; a flagged one does not, and both carry the per-tool bound (boundDetachedCall) unless the tool's own BackgroundDefault claims this call.

    Local dev builds turn this on by default: make build / make build-dev compile with -tags localdev (LOCALDEV_TAGS), which flips the default of FALCON_TOOL_BACKGROUNDING_ENABLED to on (localdev_on.go). An explicit value always wins (=false turns it off); release (-tags release), server (-tags debug), CI eval builds and go test never set the tag. Every run states its agent and mode once, before the first turn (runinfo.go): the log line agent run starting agent=… model=… timeout=… tool_backgrounding=on promote_after=42s session=… (Info, so server pods show it without --debug), and the same key=value line as a header in the TUI (AgentCallback.OnRunStart; on in local dev builds, FALCON_SHOW_RUN_INFO overrides). In the TUI without --debug, slog output is discarded (main.go sends log to io.Discard, and the default slog handler writes through log), so the background-tool log lines above need --debug there. TUI tool cards match results by tool_use id, so a backgrounded call that finishes after a newer call of the same tool completes its own card.

    It is deadline-bounded, not fire-and-forget. When the model stops calling tools, joinBackgroundBeforeAnswer waits for every outstanding call, hands them over as a user turn and takes one more loop iteration, so the answer is written with that evidence rather than without it. The wait has no budget of its own: the investigation's end-to-end deadline is already on the loop's context (executeInternal runs on execCtx, from resolveExecuteTimeout), so waiting on it is the same thing as respecting it. Nothing is dropped for being slow — only for the investigation running out of time, and then the model is told what it lost. That is safe because answer writing is not bounded by the same deadline: on DeadlineExceeded, synthesis and runTimeoutSummary both run on a fresh, deadline-independent context.

    maxBackgroundJoinRounds bounds rounds, not time — a further round only happens if the model started more work while being held. Past it the gate stops waiting but not reporting: it delivers whatever finished and names whatever it drops, once. The handover preamble is gated on endsWithStructuredOutput, so an agent that finishes through a completion tool is not steered into prose.

    Each call runs on its own child of the run context, and abandoning it cancels that child — a flag alone would leave a goroutine inside executeTool writing to rs and to the agent's MCP and large-result state. Any exit that bypasses the gate (terminal tool, iteration cap, cost cap, fatal error, cancelled context) calls abandonBackground, which cancels and then waits up to backgroundTeardownGrace for the goroutines to leave before synthesis and MCP teardown read that state. A tool that ignores its context is logged and left rather than hanging the run.

    The real output is re-recorded against the original tool_use id, so a citation on a backgrounded call verifies against what the tool returned rather than against the placeholder. See background_tools.go.

    ACE MCP transports are never reused across prompts: each one is opened by NewAgent or openAndConnectACE and closed by ReleaseMCPSession when the prompt completes. ACE's session id manager accepts an id it no longer knows (an ACE restart, or a request served by another replica) with a 200 rather than a 404, and the connect_database that follows then registers the project's external tools onto a session ACE never initialized — logging each failure server-side and still reporting success, leaving the prompt with the static tool set and no integrations. Connection reuse instead lives one layer down, in the shared MCP HTTP transport (tools_mcp.go: sharedMCPHTTPClient, newMCPRoundTripper). Project scoping is session state: connect_database({database: projectUUID}), never a tool parameter.

    MFA --> NORM["normalize/repair: unpaired tool_use, stale thinking blocks,<br/>server-tool blocks downgraded to text when the tool<br/>isn't declared this turn (serializeServerToolBlocksOnly)"]
    NORM --> CACHE["stampCacheCheckpoint — prompt-cache anchors"]
    CACHE --> API[API request messages]

    SESS -. "between investigations" .-> COMP["compressOldHistory:<br/>prior investigations' tool exchanges →<br/>compact summaries (compressForHistory)"]
    SESS -. "end of run" .-> SAVE["saveACEHistory: TurnSnapshots + messages<br/>→ ACE (durable conversation history)"]
    SAVE -.-> LOAD["next session: LoadACEHistory → a.aceHistory<br/>→ tiers above"]

    So the memory hierarchy, in one line each:

    Horizon Mechanism Lives in
    This turn streamed response + tool_results wire
    This investigation Session.Messages, trimmed/offloaded per turn process memory
    Earlier investigations, same session compressOldHistory summaries process memory
    Prior sessions ACE conversation history, injected at tier 1/2/3 ACE
    Cross-session knowledge learnings/insights (assimilated store) ACE — see MEMORY_SYSTEM.md
    Local caches/queues internal/{history,feedback} jsonl in ~/.config/neubird disk (cache, not source of truth)
    In-process learning cache internal/{learnings,tablelearnings} process memory — ConfigDB is the durable copy

    Concurrency model

    Agent struct — shared vs per-run state

    agent is long-lived; runState is created fresh per Execute and never shared, which is what makes concurrent Execute calls on one agent safe.

    Shared fields are immutable after NewAgent or carry their own synchronisation:

    Field Type Protection Notes
    baseCfg ProviderConfig immutable LLM provider credentials
    basePromptSection, schemaSection, extraSection, tableSection, insightsSection, toolHintsSection, skillsSection *MutableSection sync.RWMutex inside Prompt sections; memory-derived ones are updated by the learning caches
    skills skillsRegistry sync.RWMutex inside All loaded local skills
    mcp mcpRegistry sync.RWMutex inside Tool list + sessions; sealCache marks the cache anchor
    sentinel / watch managers sync.Mutex + atomics Background monitor lifecycles
    digestTransport Transport WaitGroup drain before close Shared by all Haiku digest calls
    interim interimState sync.Mutex + sync.WaitGroup Background summarizer state
    lastResult safeRunResult sync.RWMutex Outcome of most recent Execute
    ace aceConnector sync.Mutex + atomic.Int64 Reconnect deduplication
    memorySeenIDs, sqlLearnings, … maps dedicated mutexes Long-term-memory local caches
    agentName atomic.Value atomic Set by TUI, read by agent goroutine

    Per-run (runState): transport, buildPrompt closure, resolved allow/deny/unlock maps, progress tracker, turn snapshots, sources, charts, doc projection, structured-output state, counters. Fresh per call; closed/discarded on return.

    Transports

    1. Per-Execute transport (rs.transport) — fresh per call for the main loop; carries model, debug log; closed on return. Fully isolated.
    2. Digest transport (a.digestTransport) — created once in NewAgent, reused for all background interim-summary calls; closed in Close() only after interim.wg.Wait() drains in-flight goroutines.

    Background interim summarizer

    After each tool round, launchBackgroundSummarizer sends a snapshot copy of the current investigation's history to Haiku and emits a rolling "what we know so far" via OnInterimSummary. Invariants: one goroutine at a time (bgRunning under interimState.mu), rate-limited to one launch per 10 s, wg.Add(1) inside the mutex so Close() can never race a starting goroutine, stale results dropped via a generation counter, disabled for health/cost runs and disable_interim_summary agents. It never sets the run's confidence; its only score is the display-only provisional_confidence (see Confidence machinery).

    Prompt sections and lazySection

    PromptSection is interface{ Build() string }: StaticSection (immutable), MutableSection (RWMutex), DateSection, and lazySection (re-evaluates a closure per Build). Per run, the memory-derived sections are frozen into statics so mid-run save_learnings calls don't invalidate the Anthropic prompt cache every tool call; the skills section stays lazy when an allowlist or autoContinue is active so InjectLocalSkills lands on the next turn.

    handleInfer flow: resolve project → get/create pooled session → resolve AgentDefinition + RunConfig from request → agent.Execute with an SSE writer callback (writer/console.go renders the same stream for the CLI view; HIDDEN_STREAM_TOOLS-style visibility maps live there).

    Per-request ACE scoping rule: the server-level AceConfig never carries ProjectID. handleInfer builds a per-request scoped copy (c := *aceConfig; c.ProjectID = req.ProjectUUID). Any new handler touching ACE must follow this pattern — sharing a mutated server-level config would leak one request's project into another's.

    Session pool: sync.Map keyed "session_id" or "session_id|ace|project_uuid" → sessionEntry{agent, session, lastUsed}; background eviction of idle entries. An aceSchemaCache (keyed by project, 30-min TTL) avoids re-discovery per request.

    Job runner

    internal/jobrunner pulls prompt jobs from Redis (/v1/prompt/submit enqueues; merlin submits automated investigations). Hooks (hooks.go, hooks_memory.go, hooks_sentinel.go) run before/after each job — e.g. CheckNeedsLearning skips a MemoryAssimilator run when the project has no pending raw learnings.
