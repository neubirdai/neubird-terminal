    Verified RCA Pipeline — Working Design Document

    Goal: Design a concrete implementation, grounded in falcon's actual code, of a multi-stage verified-RCA pipeline:

    1. Context setup agent (TelemetryRecon — already created in agents/TelemetryRecon*)
    2. Hypothesis producer (investigator) — must emit structured output (RCA evidence contract: hypothesis ledger, onset timestamps, citations)
    3. Verifier — fresh context, refutes against the contract, structured verdict
    4. Judge / gate — mechanical checks in Go where possible; bounded retry loop

    Also answer: does this need subagents? How does it compare to what Cursor does?

    Motivating evidence: 5 investigations of incident 93dd10ab (swimlanemirror, Aug 15 queue backlog): only 1 of 5 (run A) found the verified root cause (producer surge vs 32-pod KEDA ceiling). The 4 wrong runs all: anchored on loud ES-master signals, never measured producer rate, cited post-peak evidence as cause, and passed citation verification anyway. Full analysis in the conversation of 2026-08-16/17; key traces in ~/Downloads/trace_*.json.

    Evidence continuity — the ledger (added 2026-08-18)

    Six shipped bugs shared one cause: the citable tool-call catalog was scoped to a single Execute while the pipeline's evidence spans stages (recon → investigator rounds → nudges → fix-ups). Each incident was patched locally (offline validation flags, citation merging, prompt boundaries) until the class was closed structurally: ai.EvidenceLedger, one per pipeline run, passed via RunConfig to every PRODUCER stage. Each producer Execute seeds its catalog from the ledger and mirrors new calls back, so cited_tool_call_idx values are continuous across recon and all correction rounds — contracts cite recon's measurements directly, carried indices survive full in-loop validation, and OfflineContractValidation was deleted. The verifier NEVER shares the ledger: the referee re-executes cited queries in a fresh evidence world — that independence is the product. Vocabulary note: "onset from the data" now includes recon's data; the investigator re-measures only for fresh values or doubted numbers.

    Judge note: stage [G]+[2] is the judge for single runs. A separate LLM "judge" only appears in the ensemble variant: N parallel investigator asks → Merger adjudicates by contract score, never majority (our 5-run sample: majority elects the wrong RCA 4:1).

    AlertCorrelator-inspired principles (added 2026-08-17 at ganesh's direction)

    agents/AlertCorrelator/SOUL.md is the production-proven template for structure+evidence discipline. Lifted into this design:

    1. Per-claim evidence gate: every ledger row and the root cause carry an evidence: []string list of concrete named signals (entities, timestamps, values) plus a citation — mirroring alerts[].evidence. "A claim you cannot back with valid evidence is not confirmed."
    2. Completeness roster: the contract gains alerts[] — every alert in the incident, exactly once, with disposition: explained_by_root_cause | separate_issue | unexplained + evidence for explained members. A root cause that silently ignores half the incident's alerts fails validation (mirrors "return every input alert exactly once; never drop one").
    3. Judgment vs hard boundaries: investigator/verifier SOULs follow AlertCorrelator's shape — judgment is free ("not a recipe"), but a Hard boundaries (not judgment calls) section + closing Non-negotiables checklist state the mechanical invariants (cause ≤ symptom onset, all ledger classes terminated, evidence per claim, ids verbatim).
    4. Vocabulary note — the contract's "onset from the data, not alert metadata" and the time-anchor principle "the alert/ticket record is authoritative for WHEN" are compatible, not in tension: the fetched alert/ticket record pins the symptom onset and the query windows (it IS citable data — you fetched it), while cause onsets come from the backing telemetry series. "Not alert metadata" forbids trusting unverified enrichment prose, not the record's own fire/filing timestamp.
    5. Exhaustive output spec: exact JSON example + field notes + "required always, even when false/[]" + honest confidence semantics ("the pipeline may gate on this, so judge it honestly").
    6. Precision over recall: a narrow verified RCA beats a broad unverified one; when evidence doesn't clear the gate, say unexplained rather than stretch.
    7. Delivery discipline: the terminal emit_result(rca.contract.v1) IS the delivery — final action, reasoning in earlier turns.

    All five ledger classes REQUIRED (Go check for class coverage) — this alone rejects runs B/C/D/E (empty input_increased row). Confirmed/refuted rows require measurement + evidence + citation (per-claim evidence gate). alerts[] roster: every incident alert exactly once; explained_by_root_cause members require evidence (completeness invariant).

    Go mechanical gate (new internal/ai/contract.go)

    Checks (all domain-agnostic, no LLM):

    1. root_cause.onset_utc <= symptom.onset_utc (kills C/E post-hoc causes)
    2. every ledger class present, none "blocked" without blocked_reason naming what was tried
    3. every citation_idx exists in toolCalls; cited result contains the onset timestamps claimed (extends T3 check)
    4. PromQL lint on cited queries: aggregation without cluster/env label while alert labels contain one → violation (kills D's diluted avg)
    5. arithmetic_closure non-empty and mentions both an inflow and a drain figure Failure → synthetic tool-result feedback into the still-open loop (same mechanism as schema validation failure), so the investigator fixes it in-session. Cheap, no new context.

    RcaVerifier agent (new agents/RcaVerifier.md + SOUL.md)

    • Fresh ask, context: [] (no session inheritance — C→B contagion showed why), small tool set: read-only query tools ONLY for spot re-execution of cited queries, no discovery tools.
    • Input: the contract JSON + resolved citation excerpts. NOT the investigator transcript (prevents anchor inheritance).
    • SOUL: "You are a referee. Attempt to refute: (a) re-run 2-3 load-bearing cited queries verbatim; (b) check each refuted/blocked ledger row was genuinely attempted; (c) hunt internal contradictions; (d) default to fail on uncertainty."
    • ends_with_structured_output: {pass: bool, violations: [{code, detail, ledger_class?}], reexecution_results: []}.

    Orchestration: where the pipeline runner lives

    Two options, recommend (a): (a) Server-side chain in askAce (internal/server): if agent def has pre_context_agent/verify_with, askAce runs the sub-asks sequentially, threading outputs. ~200 LoC; reuses everything (sessions, tracing, cost caps). Each stage is its own trace (falcon.ask children) — evaluable independently. (b) Merlin-side: FalconSubmit issues 3 sequential asks. More moving parts, crosses repo boundary, but zero falcon changes. Rejected for latency of iteration.

    Retry budget & failure posture

    • gate/verifier rounds: ≤2 each. On exhaustion do NOT block the report: publish with banner UNVERIFIED: <violations> + confidence forced to low. An SRE seeing a wrong-but-flagged report beats silence.
    • Cost: recon (~$0.3, small model) + verifier (~$0.5) on top of ~$4 investigations; ~20% overhead. Ensemble mode (3×investigator + Merger) reserved for high-risk incidents.

    Acceptance test (already owned)

    Replay incident 93dd10ab: gate+verifier must REJECT the B/C/D/E contracts (each for its specific violation: post-hoc cause / empty input row / diluted agg / unmeasured publish rate) and PASS A's. Then N fresh runs with pipeline on → measure convergence to producer-surge RCA. Evals live in evals/ (existing harness).

    Why coding agents (Cursor) feel accurate — and what transfers

    Cursor does NOT run hypothesis→verifier→judge chains. Its architecture (public info as of early 2026): single agent loop + strong retrieval (codebase embedding index), a specialized apply/diff model, and — the decisive part — cheap objective verifiers supplied by the environment: compiler, type-checker, linters, tests. The agent iterates against ground truth that costs milliseconds and never lies. Accuracy comes from tight feedback loops with an oracle, not from multi-agent structure.

    RCA has no compiler. The design above is therefore manufacturing the oracle: the mechanical gate (timestamps, ledger completeness, citation time-ranges, agg-scope lint) is the "type-checker for causal claims", and the verifier's query re-execution is the "test run". Subagents are needed only where fresh context matters (verifier independence, recon isolation) — the gate itself is plain Go and free.
