    Memory System — How Falcon Learns and Remembers

    This document explains how Falcon accumulates knowledge across investigations — from raw capture by agents to background assimilation into a searchable, vector-backed memory store.

    Overview

    Falcon uses a two-phase memory architecture to turn observations from investigations into durable, reusable knowledge:

    1. Raw capture — agents write learnings in real-time during investigations
    2. Assimilation — a background job consolidates and embeds raw learnings into a searchable store

    Memories are scoped strictly to a project, persist across sessions, and are retrieved at investigation time to guide agents toward better answers.

    Memory Types

    Type What it stores Example
    sql Query patterns and rules for specific tables/schemas "Always filter events by org_id first for performance"
    table Which tables map to which investigation scenarios "Use deployments + rollbacks for deploy-regression queries"
    user_insight User corrections, preferences, patterns, and derived facts "User prefers percentile breakdowns over averages for latency"
    tool Syntax error patterns for specific tools "Pass tables as an array of strings, not comma-separated"

    User insights have four subtypes: preference, knowledge, correction, pattern.

    Database Schema

    All memory lives in the ace PostgreSQL schema, backed by the pgvector extension.

    Raw Tables (write-first, unprocessed)

    ace.sql_learnings        — SQL rules keyed by schema_table_type
ace.table_learnings      — scenario-to-table mappings with investigation context
ace.user_insights        — user corrections, preferences, facts
ace.tool_learnings       — tool syntax error patterns keyed by tool_name

    All four tables carry a project_uuid TEXT NOT NULL column (added in migration 20260521000001_learnings_project_uuid). Every raw row starts with assimilated_at IS NULL. The background job sets this field once the row has been consolidated.

    Partial indexes on (project_uuid) WHERE assimilated_at IS NULL enable fast per-project discovery of pending work.

    Consolidated Store

    ace.assimilated_learnings
    Column Type Purpose
    id UUID Primary key
    project_uuid TEXT Project this memory belongs to (strict equality filter)
    type TEXT sql | table | user_insight | tool
    learning TEXT The consolidated knowledge
    summary TEXT 1–2 sentence executive summary
    embedding vector(512) Semantic vector for similarity search
    confidence FLOAT 0.0–1.0, set by the assimilation agent
    source_ids TEXT[] Back-references to raw row IDs
    trigger TEXT "always" = return on every query (for critical user preferences)
    schema_table_type TEXT Lookup key for SQL learnings
    investigation_type TEXT Context for table learnings
    insight_type TEXT Subtype for user insights
    tool_name TEXT Lookup key for tool learnings
    deleted_at TIMESTAMPTZ Soft-delete timestamp

    An HNSW index on embedding and a partial index on project_uuid WHERE deleted_at IS NULL support fast retrieval.

    Project Scoping

    All memory is strictly scoped to a single project. Every read and write operation filters by project_uuid = $N — there is no fallback to empty-UUID rows or cross-project sharing.

    • Raw tables — project_uuid stored on insert; unassimilated queries filter by it
    • Assimilated store — all search, upsert, merge, and delete operations include WHERE project_uuid = $N
    • save_learnings tool — reads project_uuid from MCP args or the current session
    • list_unassimilated_learnings — filters by project_uuid when provided, so the MemoryAssimilator pre-hook only fires for projects that actually have pending work

    This was tightened in #276, which removed the backward-compatibility IN ($projectUUID, '') fallback and added project_uuid to all three raw tables.

    ACE Tools (MCP)

    All memory operations are exposed as MCP tools, implemented in ace/tools/.

    save_learnings

    Writes a raw learning to the appropriate raw table.

    save_learnings(type, content, ...)
  → writes to sql_learnings, table_learnings, user_insights, or tool_learnings
  → stores project_uuid from MCP args or session context
  → assimilated_at = NULL (pending)
  → returns {"status": "ok", "type": "<type>"}

    Called by agents during or after investigations. Non-blocking.

    Source: ace/tools/save_memory/mcp_tool_save_memory.go

    load_relevant_learnings

    Retrieves ranked learnings from assimilated_learnings using hybrid search, scoped to project_uuid.

    load_relevant_learnings(query, type?, min_score?, include_raw?)
  → hybrid: vector similarity (HNSW) + text search (ts_rank) via RRF
  → fallback: keyword-only if embedding unavailable
  → returns ranked entries with relevance_score, confidence, source

    Search strategy per type:

    • SQL — exact match on schema_table_type (no vector needed)
    • Table — Reciprocal Rank Fusion (RRF) of vector + text, blended with confidence: 0.75 × RRF + 0.25 × confidence
    • User insights — vector similarity + always-trigger records appended
    • Tool — exact match on tool_name, or semantic query when tool_name is omitted

    Pass include_raw=true during assimilation to also see raw rows that haven't been written yet, enabling deduplication within the current batch.

    Returns up to 10 learnings per type, filtered at min relevance 0.35.

    Source: ace/tools/load_relevant/mcp_tool_load_relevant.go

    update_memory

    Deletes or modifies an existing memory. Called when a user corrects an agent.

    update_memory(id, action)
  → id: UUID (assimilated) or "insight-N" (raw user_insight)
  → action: "delete" (soft) or "modify" (content update)

    Cascade behavior for raw deletes:

    • Soft-deletes the raw row
    • Finds all assimilated records containing the raw ID in source_ids
    • Single-source assimilated record → auto soft-deleted
    • Multi-source assimilated record → returned as assimilated_needs_review for agent to edit

    Source: ace/tools/update_memory/mcp_tool_update_memory.go

    list_unassimilated_learnings

    Discovery tool for the MemoryAssimilator agent. Returns up to 50 rows per type from the last 10 days where assimilated_at IS NULL, filtered by project_uuid. Covers all four raw tables in a single call:

    {
  "sql_learnings":   [...],
  "table_learnings": [...],
  "user_insights":   [...],
  "tool_learnings":  [...]
}

    Restricted: agent-only (not exposed to user-facing agents).

    Source: ace/tools/list_unassimilated_learnings/mcp_tool_list_unassimilated.go

    describe_table

    Returns schema information for a table. Now also injects SQL hints from assimilated_learnings into its response (Hints []string field), surfacing relevant memory directly at query-planning time without a separate load_relevant_learnings call.

    update_learning_assimilation

    Writes an assimilation result: creates or merges into assimilated_learnings, then marks the raw row as processed.

    update_learning_assimilation(table, id, learning, summary, confidence, ...)
  → inserts new assimilated record OR merges into existing (append source_id)
  → sets assimilated_at = now() on the raw row
  → generates 512-dim embedding for table/user_insight types

    Restricted: MemoryAssimilator agent only.

    Source: ace/tools/update_learning_assimilation/mcp_tool_update_assimilation.go

    Agents

    MemoryAssimilator

    Location: agents/MemoryAssimilator.md

    A background-only agent (not user-invocable) that consolidates raw learnings into the assimilated store.

    Property Value
    Model claude-haiku-4-5 (cost-capped at $8/run)
    Timeout 15 minutes
    Schedule Every 6 hours per project (cron: 0 */6 * * *)
    User invocable No
    Session footprint None (skip_save_session: true)

    Tools available: list_unassimilated_learnings, update_learning_assimilation, load_relevant_learnings, update_memory, get_skill, get_prompt

    Skills loaded per type: memory-sql-learnings, memory-table-learnings, memory-user-insights, memory-forget-requests, memory-tool-learnings

    Pre-execution hook: Before the agent runs, CheckNeedsLearning calls list_unassimilated_learnings scoped to the project. If no pending rows exist the run is skipped entirely, avoiding unnecessary Haiku calls.

    ExecLearningsAgent

    Location: agents/ExecLearningsAgent.md

    The user-facing agent behind the Falcon Learnings tab. Reads and writes memory as part of investigation workflows.

    Property Value
    Model claude-sonnet-4-6
    User invocable Yes (Falcon Learnings tab)

    Memory workflow:

    1. Calls load_relevant_learnings for each type at the start of an investigation
    2. Searches past investigation history via search_prompts
    3. Detects gaps: investigations with no save_learnings call = unresolved knowledge
    4. Saves new learnings inline via save_learnings
    5. On user correction: load_relevant_learnings → update_memory (delete) → save_learnings (new)

    Assimilation: Per-Type Logic

    The MemoryAssimilator orchestrates five steps (defined in agents/MemoryAssimilator/SOUL.md):

    1. Call list_unassimilated_learnings to discover all pending rows for the project
    2. Call get_skill() for each type present to load its assimilation rules
    3. Process each batch using the loaded skills
    4. Handle any [FORGET] rows via the memory-forget-requests skill
    5. Report total rows assimilated and forget requests processed

    Critical rule across all types: always pass include_raw=true when calling load_relevant_learnings during assimilation, so raw rows from the current batch are visible for deduplication before they are written.

    SQL Learnings (memory-sql-learnings)

    Skill: skills/memory-sql-learnings/SKILL.md

    SQL learnings are upserted — one active assimilated record exists per schema_table_type. Subsequent raw rows update that record rather than creating duplicates.

    For each raw sql_learnings row:

    1. Call update_learning_assimilation with:
    2. table="sql_learnings", the row ID, generalized learning, summary, confidence, schema_table_type
    3. This upserts by schema_table_type, updating the existing record if one exists

    SQL hints are served directly via describe_table, which queries assimilated_learnings and injects relevant hints into its response. There is no separate table-comment update step.

    Confidence bands:

    Range Meaning
    > 0.8 Generic rules applicable across many environments
    0.5 – 0.8 Patterns applicable to recognizable situations
    < 0.5 Narrow, investigation-specific facts

    Table Learnings (memory-table-learnings)

    Skill: skills/memory-table-learnings/SKILL.md

    Table learnings accumulate over time and are merged when a new row is semantically identical or very similar to an existing one.

    For each raw table_learnings row:

    1. Validate against investigation context (if prompt_id present):
    2. Call get_prompt() to retrieve the investigation
    3. Cross-reference tool calls and final_answer to validate which candidate tables actually had evidence
    4. Update the tables field to only include validated tables
    5. If get_prompt fails → treat as no context, proceed with confidence 0.5

    6. If investigation status is not COMPLETED or confidence < 0.5 → mark inconclusive (confidence 0.1)

    7. Deduplicate via load_relevant_learnings(type="table", include_raw=true):

    8. Identical → merge with merge_into_id=<existing_id> (no new record)
    9. Same insight, slight variation → merge with updated learning capturing both cases; increase confidence by ≤ 0.1
    10. Multiple near-duplicates → delete all but the highest-confidence record, merge into the survivor

    11. Different insight → proceed to step 3

    12. Insert as new via update_learning_assimilation with table_learnings data

    User Insights (memory-user-insights)

    Skill: skills/memory-user-insights/SKILL.md

    User insights are merged or inserted based on semantic similarity. The trigger field controls whether a preference is always returned or only returned on semantic match.

    For each raw user_insights row (excluding [FORGET] rows):

    1. Deduplicate via load_relevant_learnings(type="user_insight", include_raw=true):
    2. Identical → merge with merge_into_id=<existing_id> (no new record)
    3. Same belief, updated → call update_memory(action="modify") on the existing record, then merge the raw row via merge_into_id
    4. Multiple near-duplicates → delete all but highest-confidence survivor, then modify + merge into it

    5. Different insight → proceed to step 2

    6. Insert as new via update_learning_assimilation with:

    7. trigger="always" only for insight_type="preference" (e.g. "always show p99 latency") — these are returned on every query regardless of search relevance
    8. trigger unset for knowledge, correction, pattern — returned only by semantic similarity

    Forget Requests (memory-forget-requests)

    Skill: skills/memory-forget-requests/SKILL.md

    Any user_insights row whose content starts with [FORGET] is treated as an erasure request rather than a new learning.

    For each [FORGET] row:

    1. Extract the subject from the content after the [FORGET] prefix
    2. Call load_relevant_learnings(type="user_insight", query=<subject>) to find matching records
    3. For each match, call update_memory(action="delete", id=<id>) to soft-delete it
    4. If no match found, no action needed — the raw row was never assimilated

    Tool Learnings (memory-tool-learnings)

    Skill: skills/memory-tool-learnings/SKILL.md

    Tool learnings are upserted — one active assimilated record exists per tool_name. Subsequent raw rows update that record rather than creating duplicates.

    For each batch of raw tool_learnings rows:

    1. Group by tool_name
    2. Compile a concise hint block noting bad patterns, correct forms, and frequency
    3. Call update_learning_assimilation with table="tool_learnings", row ID, compiled learning, summary, confidence, tool_name

    Full Data Flow

    Investigation (ExecLearningsAgent / Analyst)
  │
  ├── load_relevant_learnings(query, project_uuid)
  │     └── hybrid search on assimilated_learnings WHERE project_uuid = ?
  │           → returns ranked context for agent
  │
  ├── agent reasons, executes SQL, presents findings
  │
  └── save_learnings(type, content, project_uuid, ...)
        └── writes to raw table with project_uuid (assimilated_at = NULL)

                         ↓  (every 6 hours, per project)

Memory Assimilation (MemoryAssimilator)
  │
  ├── [pre-hook] CheckNeedsLearning(project_uuid)
  │     └── aborts if no pending rows for this project
  │
  ├── list_unassimilated_learnings(project_uuid)
  │     └── up to 50 rows per type, last 10 days
  │
  ├── get_skill for each type present
  │
  ├── SQL learnings:
  │     └── upsert by schema_table_type into assimilated_learnings
  │
  ├── Table learnings:
  │     ├── validate against investigation context (get_prompt)
  │     ├── deduplicate via load_relevant_learnings (include_raw=true)
  │     └── insert new or merge into existing
  │
  ├── User insights:
  │     ├── deduplicate via load_relevant_learnings (include_raw=true)
  │     ├── set trigger="always" for preferences only
  │     └── insert new or merge/modify existing
  │
  ├── Tool learnings:
  │     └── upsert by tool_name into assimilated_learnings
  │
  └── [FORGET] rows:
        ├── find matching assimilated records
        └── soft-delete each match

                         ↓

Next investigation:
  ├── describe_table(table) → hints from assimilated_learnings injected into response
  ├── tool descriptions loaded → hints from assimilated_learnings appended to description
  └── load_relevant_learnings(type="tool") → tool hints injected into ## Tool usage rules section

    Learning Queue

    Location: internal/ai/learning_queue.go

    A background worker pool (2 goroutines) that persists learnings from Falcon agents to ACE asynchronously. Each job carries a project_uuid because background sessions are not connected to a database session.

    Key Design Decisions

    Strict project isolation — All queries use project_uuid = $N with no cross-project fallback. Removed in #276 was the IN ($projectUUID, '') pattern that had allowed org-wide system records.

    Soft deletes everywhere — deleted_at timestamps preserve audit history and allow undo. Queries always filter WHERE deleted_at IS NULL.

    Two-phase architecture — Raw capture is non-blocking; expensive operations (embedding generation, deduplication, merging) happen asynchronously in the background job.

    Assimilation idempotence — SQL learnings upsert by schema_table_type (one record per table). assimilated_at prevents the same raw row from being processed twice.

    Hybrid search with graceful degradation — Vector + text search combined via RRF for table and user insight types. Falls back to keyword-only search if the embedder is unavailable.

    Multi-source merge tracking — source_ids TEXT[] links each assimilated record back to its raw sources, enabling safe cascade deletes and transparent lineage.

    Always-trigger preferences — User insights of subtype preference are tagged trigger="always" so they are returned on every load_relevant_learnings call, regardless of semantic similarity. Other subtypes are returned only when the query matches.
